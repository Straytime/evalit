# 产品背景

evalit 是一个 Agent / LLM 评测工具，基于指定的测试集，对远程/本地的 Agent 服务或单个 prompt 进行批量测试，并对测试结果进行评估。工具支持联动私有化 Langfuse，将其中的 Dataset 作为测试数据来源，并根据 Agent 返回的 Trace ID 读取 Trace 作为评估数据来源。

Demo 阶段，Langfuse 仅向 evalit 提供 Dataset 和 Trace。evalit 不向 Langfuse 创建或更新 Dataset、Experiment、Score 等数据；评估计划、评估运行和评估结果均由 evalit 自身保存、展示并导出。

产品形态：macOS 本地应用，demo 级落地，不涉及完整的系统需求和外围 user case。

> evalit 将 Langfuse Dataset、外部 Agent 服务和 Agent Trace 连接起来，通过可视化的数据映射与可复用 Evaluator，让非研发用户无需编写 Experiments via SDK 脚本，也能完成面向最终输出和执行轨迹的批量评测。
> Langfuse 负责记录发生了什么；evalit 负责定义如何运行 Agent，以及如何基于最终输出和轨迹判断它做得对不对。

| Langfuse 的关键局限                                                                          | 对 Agent 评测的影响                                           | evalit 对应解决方案                                                  | 突出价值                       |
| --------------------------------------------------------------------------------------- | ------------------------------------------------------- | -------------------------------------------------------------- | -------------------------- |
| Langfuse UI 没有调用 Agent 的能力，需要自行编写 Task Function                                         | 每接入一个 Agent，都要编写请求、认证、响应解析等代码                           | 配置 Agent URL、鉴权、请求结构、响应结构和连通测试                                 | 降低评估对象接入门槛，减少重复开发          |
| Dataset 与 Agent 请求之间的适配需要在 SDK 代码中完成                                                    | Dataset Schema 或 Agent API 变化时需要修改脚本                    | 在评估计划中可视化配置 Dataset → Agent 输入映射，支持 JSON 字段路径下钻                | 数据关系透明、可复用、便于排查            |
| 内置 Evaluator 主要接收目标 Observation、Trace 根输入输出或 Experiment Item 上下文，无法离线观测完整 Observation 树 | 无法直接判断整条轨迹是否使用过某个工具、调用顺序是否合理                            | evalit 按 Trace ID 拉取 Trace，并将指定 Observation 及全部子节点传给 Evaluator | 将 Agent 轨迹变成一等评估对象         |
| via SDK 可以实现复杂数据组装，但需要工程师编码                                                             | 产品经理或评测人员无法独立创建和调整评估方案                                  | 管理测试集、评估对象、Evaluator 和评估计划                                     | 将一次性 SDK 脚本转化为可复用产品流程      |
| LLM 评估器有固定黑盒模板，不透明，输出不一定稳定遵守预期结构                                                        | JSON 缺失字段或类型错误时，可能产生不可用结果，却无法透明调优                       | 完全自定义prompt，同时定义严格输出契约；运行时校验必填 Key、类型和 Categorical 选项          | 保留 Prompt 自由度，同时保证统计确定性    |
| Langfuse 缺乏有效、直观的评测统计与快速导出能力                                                            | 评测后的数据分析与处理受限                                           | 每个指标同时展示有效结果数、计划总数、失败数和不可评估数+指标输出+附件导出                         | 直观输出各项数据并直接导出，提高评测效率与可信度   |
| Langfuse Dataset、Trace、Experiment 和 Score 主要以 Project 为数据边界                             | Dataset 与 Agent Trace 位于不同 Project 时，不容易组成统一 Experiment | evalit 分别配置 Dataset 来源 Project 和 Trace 来源 Project              | 支持跨 Langfuse Project 的评测编排 |
| Langfuse 本地 Dataset 的 via SDK 运行不会形成完整 Dataset Run 体验                                   | 本地 Dataset 与 Langfuse Dataset 的结果体验不一致                  | evalit 将本地 CSV 和 Langfuse Dataset 统一为内部测试集                     | 用户不需要理解两类 Dataset 的平台差异    |
| Langfuse 结果查看主要服务于在线分析和平台内对比                                                            | 用户想自行组合字段或做临时业务分析时不够自由                                  | 导出 Dataset、Agent Output、Trace 证据、全部指标、状态和错误到 Excel             | 适合灵活分析、共享和离线留档             |

# 名词说明

| 名词           | 定义                                                                        | 备注  |
| ------------ | ------------------------------------------------------------------------- | --- |
| evalit       | 产品名称                                                                      |     |
| 测试集          | 一组用于 Agent/prompt 测试的输入数据，可以关联 Langfuse 中的 `Dataset`，也可以从本地文件导入           |     |

## User function spec

### func_1_langfuse 项目管理

用户集中管理 Langfuse Project 信息，以在其他功能模块中读取 Dataset 和 Trace。

支持概览所有已配置的 langfuse project，可查看 project 详情或删除

- 详情中的 key 信息需脱敏显示

新增 langfuse project：

1. 用户手动提供以下信息并提交
   - base url
   - Public Key
   - Secret Key
2. 校验、添加 langfuse project
   - 校验成功后自动获取 project name 作为 evalit 中的 langfuse 项目名称
   - 不允许重复添加已存在的 project

evalit 中所有读取 Langfuse Dataset 和 Trace 的能力，均通过在此维护的 Project 信息完成。Demo 阶段不通过这些 Project 连接向 Langfuse 写入任何数据。

### func_2_LLM 管理

集中管理 LLM model，支撑 evalit 中所有的基础 LLM 调用。

支持 Open AI Compatible 的 LLM 接入，不做 供应商区分

1. 用户提供以下信息并提交
   1. base url
   2. API key
   3. model code（list）
2. 校验模型服务连通性并添加 LLM

evalit 中所有涉及 LLM 的能力，均通过在此维护的 LLM 信息进行调用。

### func_3_测试集-管理

测试集相关能力统一入口，可选择两种方式新建测试集，或删除已有的测试集。

1. 展示所有的已存在测试集列表
   - 测试集名称
   - 测试集中测试用例数量
   - 测试集创建时间
2. 可删除或归档测试集
   - 未被任何评估计划或评估运行引用时，可在二次确认后永久删除
   - 已被评估计划或评估运行引用时，不允许永久删除，只能归档
   - 归档后不再允许用于新建评估计划，但历史评估计划与运行记录仍可正常查看
3. 新建测试集，可选两种方式
   - langfuse 导入关联（func_4_测试集-langfuse 导入）
   - 本地导入（func_5_测试集-本地导入）

> 测试用例格式定义，每条测试用例包含三个数据字段
> 
> - metadata：补充元数据，选填
> - expected output：预期输出，选填
> - input：测试的输入，必填

### func_4_测试集-langfuse 导入

自动从 langfuse project 中识别 dataset，选择、导入 evalit 作为测试集。

1. 根据已维护的 langfuse project 信息，展示所有 dataset
   - 所属 project 名称
   - dataset 名称
   - dataset 中的 item 数量
   - dataset 创建时间
2. 可预览具体 dataset 中内容
   - 预览展示 input、expected output、metadata
   - 支持分页，总计最多展示 50 条
3. 用户选择要导入关联的一个或多个 dataset，导入到 evalit
   - 选择多个 dataset 时在 evalit 内生成对应多个测试集，不做合并
   - dataset 数据原生与测试用例格式定义一致，直接关联
   - 不能重复导入已导入过的 dataset
4. langfuse 导入的测试集只维护关联关系，不做数据的长期存储
   - 为保证数据统一和时效，langfuse 导入的测试集在实际调用时，必须实时拉取整个 dataset 作为快照，禁止提前缓存

### func_5_测试集-本地导入

从用户本地设备上选择文件导入，作为 evalit 的新建测试集。

1. 用户手动设定测试集名称，选择本地文件上传
   - 仅支持单个
   - 仅 csv
2. 文件内容校验
   - 至少包含一个数据列 + 一个数据行（不含表头行）
3. 可预览上传文件中识别到的数据内容
   - 预览展示所有已解析数据列
   - 支持分页，总计最多展示 50 条
4. 提取所有表头行，用户手动映射到测试用例数据字段（input、expected output、metadata）
   - 同一表头只能映射到一个字段
   - 支持多个表头组合映射到同一个字段
     - `a,b → {"a": "...", "b": "..."}`
5. 配置映射后，展示 input、expected output、metadata 值预览
6. 用户确认提交，校验映射并生成测试集
   - input 不能为空
   - 多表头-单字段时，自动将多个表头数据组合为 json，并校验 json 是否合法

### func_6_评估器-管理

评估器管理统一入口，可创建新的评估器或删除已有评估器。

1. 按列表展示所有已有的评估器
   - 评估器名称
   - 评估器类型（代码/LLM）
   - 创建时间
2. 可删除或归档已有评估器
   - 未被任何评估计划或评估运行引用时，可在二次确认后永久删除
   - 已被评估计划或评估运行引用时，不允许永久删除，只能归档
   - 归档后不再允许用于新建评估计划，但历史评估计划与运行记录仍可正常查看
3. 新建评估器，两种类型
   - 代码评估器（func_7_评估器创建-代码）
   - LLM 评估器（func_8_评估器创建-LLM）

### func_7_评估器创建-代码

创建 TS 或 JS 的代码评估器，定义输入变量和输出指标。

1. 用户自定义评估器名称，并编写 TS/JS 代码用于评估
   - 评估器名称不可重复
2. 纯沙盒执行器，禁止文件、环境变量、网络和子进程访问等必要的沙盒安全限制，仅支持 TS/JS 默认库和必要的补充内置库
   - 代码评估器的典型场景包括精确匹配检查、正则表达式验证、JSON 可解析性、模式验证、关键词检查、工具调用检查以及自定义业务规则等
   - 执行超时时间 5s，输出大小上限 100k 字节
3. 用户需手动声明代码评估器的输入数据变量并在代码中使用
   - 至少要有一个变量
4. 代码评估器必须明确定义输出的评估指标
   - 每个指标需定义唯一的 Key 和类型
   - 支持 `numeric`、`boolean`、`text` 和 `categorical`
   - `categorical` 指标必须同时定义全部允许的分类选项
5. 用户提交后，系统校验代码语法、格式和输出指标定义后保存
   - 支持用户提供示例输入并试运行，提前检查代码输出是否符合已定义的输出契约
   - 创建时的校验不能保证代码所有运行分支均返回相同结构，实际运行时仍需严格校验每次输出

### func_8_评估器创建-LLM

创建基于 LLM 的评估器，编辑 prompt、调用参数，定义输入变量和输出指标。

1. 从已配置的 LLM  中选择要使用的评估 LLM
   - 未配置 LLM 时不允许创建 LLM 评估器
   - 支持手动指定 LLM temperature 和 top_p
2. 用户自定义评估器名称，并编写评估器 LLM 的 system prompt 和 user prompt
   - 评估器名称不可重复
   - system prompt 和 user prompt 的具体内容由用户完全自定义
3. 支持在 prompt 中通过双括号创建自定义变量
   - 至少要有一个变量
4. 用户必须定义 LLM 评估器预期输出的评估指标
   - 每个指标需定义唯一的 Key 和类型
   - 支持 `numeric`、`boolean`、`text` 和 `categorical`
   - `categorical` 指标必须同时定义全部允许的分类选项
5. LLM 评估器的输出必须为 JSON 对象，支持以下两种形式
   - 直接输出 JSON 对象
   - 输出由单个 Markdown 围栏包裹的 JSON 对象
6. 用户提交时，系统校验输入变量、输出指标和 Prompt 中的变量引用后保存
   - 支持用户提供示例变量并试运行，提前检查 LLM 输出是否符合已定义的输出契约
   - 创建时试运行成功不代表后续输出一定符合契约，实际运行时仍需严格校验每次输出

#### 补充说明：评估器输出指标与结果校验规则

LLM 评估器和代码评估器使用统一的输出指标定义与运行时校验规则。

1. 输出指标类型
   - `numeric`：值必须为 JSON number；`0` 是有效值
   - `boolean`：值必须为 JSON boolean，只接受 `true` 或 `false`；`false` 是有效值
   - `text`：值必须为非空字符串
   - `categorical`：值必须为非空字符串，且必须属于创建指标时定义的分类选项
2. 输出指标 Key
   - 同一个评估器内的已定义 Key 不允许重复，Key 区分大小写
   - 评估器实际输出时，所有已定义的 Key 都必须存在且值不能为空
   - `null`、空字符串和仅包含空白字符的字符串均视为空；`0` 和 `false` 不视为空
   - 允许输出未定义的额外 Key；额外 Key 保留在单条评估结果中供查看和导出，但不参与类型校验和聚合统计
3. 输出格式解析
   - 输出根节点必须是 JSON 对象，不支持以数组或其他类型作为根节点
   - 直接输出 JSON 时，JSON 前后不允许包含解释文字或其他内容
   - 使用 Markdown 围栏时，只允许存在一个围栏，围栏内只能包含一个 JSON 对象，围栏前后不允许包含其他内容
4. 运行时严格校验
   - JSON 无法解析、缺少任一已定义 Key、已定义 Key 的值为空、值类型不匹配或 `categorical` 值不在允许选项中时，整个评估器本次执行标记为 `failed`
   - `failed` 表示评估器执行或输出校验失败，不等价于某个 `boolean` 指标返回 `false`
   - 校验失败时记录具体错误类型、字段、预期类型和实际值类型；针对 LLM 评估器，不展示无法解析的原始输出

### func_10_评估对象创建-Agent

配置目标服务信息，定义、调试输入和输出 schema，创建待评估的 Agent。

1. 自定义 Agent 名称，通过多种可选方式配置 Agent 服务调用
   - 需先选择阻塞式 or 流式服务，默认为阻塞式
2. 第一种，通过标准 HTTP 服务的方式关联 Agent，纯手动配置，参考 Postman 手动调用配置逻辑
   - 完整请求目标 url（base+endpoint）
   - 请求方法
   - 自定义 headers
   - 鉴权（如有）
     - 支持常见鉴权方式
   - json 请求体 schema（需校验）
3. 第二种，curl 导入。
   - 用户输入 curl 命令，解析命令获取目标 agent 服务的调用方式
   - 只解析 curl 文本，绝不执行命令或 $()、反引号、文件引用
4. 第三种，openAPI 3.0 规范的 API schema 导入
   - 导入后，解析其中的 Operation。
   - 用户选择一个 Operation，系统自动填充请求方法、URL、请求 Schema、响应 Schema 和鉴权方式
     - 此处的响应 schema 仅供参考，后续同样必须以调用校验输出为准
   - 用户可手动编辑实际服务地址
   - 用户必须提供鉴权凭证
5. 服务调用配置中，支持自定义将某个/某几个 header 的值设为变量，仅支持字符串
6. 完成服务调用配置后，手动配置请求体的所有值来源（MVP 明确只支持带 JSON Body 的 HTTP API）
   - 固定值：手动写死
   - 空值：固定留空
   - 调用变量值：设为输入变量，在批量调用、评测时，使用测试用例动态构建
7. 强制进行调用校验
   - 进行调用测试，用户提供所有调用必需的输入
   - 尝试调用服务，若失败或报错，展示错误信息并允许用户返回调整
     - 调用成功需缓存完整响应，用于后续响应 schema 构建
8. 调通后获取响应 schema，区分阻塞式与流式两种获取流程，流式仅支持标准 SSE
   - 阻塞式，自动解析响应，获得响应 schema
     - MVP 不支持手动增删改，防止实际评测时不可用
   - 流式，需按照 event 解析还原规则，生成 schema
     - 自定义解析规则
       - 可选提供 SSE 响应说明（标准接口说明/API schema/手写说明）
       - 调用当前用户已配置的 LLM 服务，输入测试调用的「请求体」+「完整 SSE event」+「SSE 响应说明」，生成 event 解析规则
         - 若当前用户未配置任何 LLM，则不支持继续，必须配置 LLM
       - 使用生成的解析规则进行还原，输出还原结果
       - 用户确认解析规则 + 输出结果，获得响应 schema
       - 若还原结果不符合预期，支持用户调整后再生成，具体约束：
         - 调整方式是变更 SSE 响应说明，再次生成
         - 不支持「连续多轮交互」进行调整，SSE 响应说明是用户唯一的输入手段
         - 负责规则生成的 LLM 也不存在 history message，每次只输入当前测试调用的请求体、event、响应说明
       - 以上规则配置与调用验证流程需强制执行不可跳过
     - 实际调用时，以连接关闭作为流式响应完成信号
9. 独立 Agent trace 配置（可选开启），支持三种配置方式选择
   - 方式一，Agent 服务返回 trace ID
     - 从响应 schema 中，手动选择 trace id 对应的字段
     - 从已有 langfuse 项目中，选择关联项目
     - 实际逻辑为，使用指定的响应字段值，作为 trace ID，从 langfuse project 中异步拉取 trace 信息
     - 使用此方式时，需再进行一次试运行，校验 trace 获取是否成功
   - 方式二，注入 trace 到 agent 服务
     - evalit 在调用 agent 时构造完整 W3C traceparent，直接生成 trace ID 并传递给 agent 服务
       - 需要 agent 支持 traceparent
     - 从已有 langfuse 项目中，选择关联项目
     - 实际逻辑为，直接使用生成的 trace ID，从 langfuse project 中异步拉取 trace 信息
     - 使用此方式时，需再进行一次试运行，校验 trace 获取是否成功
   - 方式三，自定义 metadata 字段。此方式作为兜底，仅适用于：agent 服务会将响应中的字段 A 的值 x，写入到 trace 信息里 metadata 中的字段 B
     - 从响应 schema 中，手动选择关联字段 A
     - 手动输入 langfuse metadata 字段名 B
     - 从已有 langfuse 项目中，选择关联项目
     - 实际逻辑为，使用响应的关联字段 A 的值，精确匹配 langfuse project 中 metadata.B 的值，使用查询结果中的 trace ID 获取 trace 信息并按 trace ID 去重
       - 字段 A 的值不能为空
       - 限制查询最近一天
     - 使用此方式时，需再进行一次试运行，校验 trace 获取是否成功
   - 无论使用何种方式，实际拉取时机发生在 Agent 响应完成之后，固定间隔 10s 轮询，最多等待 60s
     - 0 个 trace：继续轮询，直到 60s 上限
     - 1 个 trace：继续轮询，直到连续两次拉取结果完全一致，或达到 60s 上限，都视为拉取完成
       - 60s 内最后两次拉取结果不一致时，取最后一次拉取结果
     - 多个 trace：视为拉取失败，不向下游传递任何 trace 信息
10. 服务测试连通，信息完备后，保存并建立待评估 Agent

   - 需校验评估对象必填输入变量、评估器输入变量已映射无缺失

#### 补充说明：Agent Trace Observation 选择规则

Demo 阶段采用基于 Observation 名称的简化选择方式：

1. 用户输入 Observation 名称，系统在当前测试用例对应的 Trace 中进行名称精确匹配
   - 名称匹配区分大小写
2. 返回所有同名 Observation，而不是只选择第一条
   - 每条匹配结果同时包含该 Observation 自身及其全部子节点
   - 同一个 Observation 被多个匹配子树覆盖时只保留一次，避免重复输入
   - 最终作为 Observation 子树数组传入所关联的评估器变量
3. Trace 已拉取但没有匹配结果时，向评估器传入空数组，由评估器自行判断其业务含义
4. Trace 缺失时，不执行依赖该 Trace 变量的评估器，并将本条结果标记为 `not_evaluable`

后续完整实现可在该规则基础上扩展：

- 支持按 Observation 类型、名称、层级路径和 metadata 组合筛选
- 支持精确匹配、模糊匹配、正则表达式以及单条/全部结果数量约束
- 支持选择是否包含父节点、子节点或完整 Trace
- 支持在创建评估计划时使用真实 Trace 预览选择结果和最终变量内容
- 支持对不同 Agent 框架产生的 Trace 进行标准化，形成统一的 trajectory 数据结构
- 支持为找不到节点、匹配多条和 Trace 不完整分别配置处理策略

### func_14_评估计划-执行

执行已配置完成的评估计划并生成评估结果。

1. 选择已配置的评估计划执行
2. 自定义执行条数
   1. 可选仅执行测试集中 top N 测试用例（按数据源原始顺序）
3. 自定义执行并发
   1. 待评估 Agent/prompt 请求并发
   2. LLM 评估器执行并发（如有）
4. 确认并执行评估计划
   - 开始执行前，对本次运行使用的测试集、评估器、评估对象、完整评估计划设置建立持久化快照，按「评估执行」维度保存
5. 评估运行包含以下状态
   - `pending`：已创建，等待开始执行
   - `running`：至少一个测试用例正在执行
   - `completed`：所有计划执行的测试用例均 completed，评估结论为不通过不影响该状态
   - `partially_completed`：运行已结束，至少一个测试用例为 `completed`，且至少一个测试用例为 `failed`
   - `failed`：运行初始化失败，或所有测试用例均为 `failed`
6. 单条测试用例包含以下状态，评估对象为 `failed` 或 `not_evaluable` 后，未执行的评估器统一记录为 `not_evaluable`，保证每个“用例 × 评估器”都有统计状态；所有可继续执行的评估器进入终态后，再汇总测试用例最终状态
   - `pending`：等待执行
   - `target_running`：正在调用评估对象
   - `waiting_for_trace`：评估对象已返回，正在等待并拉取 Trace；不需要 Trace 时跳过
   - `evaluating`：正在执行一个或多个评估器
   - `completed`：评估对象 `success`，且所有评估器均为 `success`
   - `failed`：评估对象为 `failed` / `not_evaluable`，或至少一个评估器为 `failed` / `not_evaluable`
7. 每次评估对象执行包含以下状态
   - `success` ：评估对象运行成功
   - `not_evaluable` ：输入缺失，包括字段路径未命中
   - `failed` ：超时、报错或结果解析失败等错误
8. 每次评估器执行包含以下状态
   - `success`：评估器成功执行，且结果可被系统正常解析；该状态只表示评估过程成功，不代表业务结论通过
   - `not_evaluable` ：输入缺失，包括字段路径未命中
   - `failed`：超时、报错或结果解析失败等错误
9. 基础失败恢复机制
   - 单条测试用例或单个评估器失败时，不中断其他测试用例和评估器
   - 每个阶段完成后保存已产生的 Agent/prompt 输出、Trace 和评估结果，避免进程异常后丢失全部进度
   - 默认不自动重试且不支持重试，避免重复调用 Agent 产生副作用或重复消耗 LLM 费用，避免未定义的数据冲突
10. 评估执行完成后，所有结果和产出物写入持久化快照中，同样按「评估执行」维度保存

### func_15_评估执行管理

统一查看所有评估执行以及执行结果详情。

1. 进行中的评估计划执行
   - 待评估的 Agent/prompt 已执行的测试用例进度
   - 评估器已评估的测试用例进度
     - 多个评估器时独立统计展示
2. 已完成的评估计划执行
   - 按测试用例列表展示所有评估结果、结果状态和失败原因
     - 针对 LLM 评估器，自动按 json 格式解析评估器输出；无法解析时标记为 `failed`，不展示 LLM 评估器原始输出
   - 按评估器分组，展示该评估器全部已定义输出指标
     - `numeric`：展示每条有效结果的数值，并统计有效结果数量、平均值、最小值和最大值
     - `boolean`：展示每条有效结果，并统计 `true` 数量、`false` 数量和 `true` 在有效结果中的占比
     - `categorical`：展示每条有效结果，并按预定义分类选项统计数量及其在有效结果中的占比
     - `text`：按测试用例展示具体内容，不进行好坏判断或聚合统计
     - Demo 阶段不默认将数值高低、`true/false` 或某个分类解释为好坏，也不据此生成统一的通过率
   - 所有输出指标统计必须同时展示结果覆盖情况
     - 分别展示 `success`、`not_evaluable` 和 `failed` 的用例数量
     - Numeric 平均值、Boolean True 占比和 Categorical 分类占比只使用 `success` 结果计算，并同时展示有效结果数与计划执行总数
     - 未定义的额外 Key 只在单条结果中展示，不参与聚合统计
   - 支持导出为 excel
     - 导出内容应包含测试用例数据、评估对象输出、所有已定义输出指标、额外 Key、评估器结果状态、失败原因

### func_16_版本与变更

基于版本对 evalit 中的关键对象进行管理。

2. 首次创建时版本为 `0.1`
3. 发生变更并保存时，以 `.1` 为步长，自动更新版本 & 版本号，
   - 最多保留 10 个历史版本（包含当前版本）
4. 版本回滚
   - 测试集回滚前必须校验以下条件，不符合条件的禁止回滚
     - 没有标准字段映射被移除，回滚目标版本必须包含当前版本的全部“表头 → 标准字段”映射关系，不允许任何已有映射关系被移除。
   - 评估对象回滚必须校验以下条件，不符合条件的禁止回滚
     - agent trace 配置，不存在 `开启 --> 关闭`
   - 评估器回滚没有限制
   - 评估计划回滚没有限制
   - 可手动选择回滚到指定历史版本
   - 回滚实际行为是**复制**指定版本内容**生成新版本**，即版本号会正常更新

> `0.9` 的下一版本是 `1.0`

### func_17_测试集编辑

对已创建的测试集进行管理。

langfuse 导入测试集的唯一合法来源是 langfuse dataset 本身，禁止编辑，若需要调整需在 langfuse 中进行变更；

本地导入的测试集可以手动编辑：

1. 可编辑内容
   - 手动增加测试用例
   - 手动删除测试用例
     - 至少保留一条
   - 手动编辑单条测试用例中，各列的值
   - 调整表头与测试用例标准数据字段的映射关系（input、expected output、metadata）
     - 不支持编辑表头本身
     - 不支持从标准字段中移除映射
     - 只支持新增映射到标准字段
       - 不支持单字段映射变更为多字段组合映射
     - 同一表头只能映射到一个字段
     - 支持多表头组合映射到同一字段，示例：`a,b → {"a": "...", "b": "..."}`
2. 编辑完成后保存
   - 已关联计划的测试集，需明确列出变更会影响的计划
   - 重新校验映射（与创建时要求一致）
     - input 不能为空
     - 多表头-单字段时，自动将多个表头数据组合为 json，并校验 json 是否合法
   - 生成新版本

### func_18_评估对象编辑

对已创建的评估对象进行编辑。

**Agent 对象**

1. 阻塞 / 流式服务类型不可变更
2. 可手动编辑服务调用配置，仅支持手动编辑，不可 curl 或 schema 导入
   - 只可编辑请求 metadata（ method / endpoint / headers）
     - header 的变量配置完全不可调整：已有变量 header 不可编辑或删除，现存及新增的非变量 header 均不可设为变量
   - 请求体 schema 不可变更
   - 请求体中，值的来源设置：
     - 固定值，可变更为新的固定值或空值，不可变更为调用变量值
     - 空值，可变更为固定值，不可变更为变量值
     - 调用变量值，不可调整
   - 编辑后强制调用校验
     - 进行调用测试，用户提供所有调用必需的输入
     - 尝试调用服务，若失败或报错，展示错误信息并允许用户返回调整
     - 调用成功需缓存完整响应，用于后续响应 schema 校验和可能的 Agent trace 构建
3. 响应 schema 不可编辑
   - 编辑后调用测试产生的实际响应必须符合已锁定的响应 Schema，否则禁止保存新版本
4. Agent trace 配置编辑
   - 应用「与创建时相同的」完整 trace 配置流程 & 选项 & 要求
   - 已开启 Agent trace 配置的服务，不允许关闭
   - 未开启 Agent trace 配置的服务，可以开启并配置
5. 编辑完成后保存
   - 已关联计划的评估对象，需明确列出变更会影响的计划
   - 生成新版本

**prompt 对象**

1. 可编辑 system prompt 和 user prompt
   - prompt 中的变量软锁定，不允许出现新变量，也不允许丢弃旧变量，实时校验提醒
2. 支持编辑 temperature 和 top_p
3. 编辑完成后保存
   - 已关联计划的评估对象，需明确列出变更会影响的计划
   - 生成新版本

### func_19_评估器编辑

对已创建的评估器进行编辑。

**代码评估器**

1. 可编辑内容
   - 支持编辑沙盒代码
   - 不支持变更沙盒语言，不支持变更输入变量和输出指标
2. 编辑完成后保存
   - 已关联计划的评估器，需明确列出变更会影响的计划
   - 重新校验代码语法
     - 支持提供测试输入并试运行
   - 生成新版本

**LLM 评估器**

1. 可编辑内容
   - 支持编辑 system prompt 和 user prompt
     - prompt 中的变量软锁定，不允许出现新变量，也不允许丢弃旧变量，实时校验提醒
   - 支持编辑 temperature 和 top_p
   - 不支持变更输出指标
2. 编辑完成后保存
   - 已关联计划的评估器，需明确列出变更会影响的计划
   - 校验变量是否发生变化
     - 支持提供测试变量值并试运行
   - 生成新版本

### func_20_评估计划编辑

对已创建的评估计划进行编辑

1. 仅支持编辑映射关系
   - 测试集 --> 评估对象输入变量映射（包括 header 变量映射）
   - 测试集 & 评估对象输出 --> 评估器输入变量映射
2. 不可变更计划中的测试集、评估对象、评估器，评估计划只记录三元组的组合关系，每次计划执行时，永远使用计划内三元组各自实际生效的版本
   - langfuse dataset 测试集是例外，没有版本
3. 编辑完成后保存
   - 校验所有必填 Agent 输入变量（包括 header）均已映射
   - 校验所有评估器输入变量均已映射
   - 生成新版本
