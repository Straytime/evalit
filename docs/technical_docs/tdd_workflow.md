# 严格 TDD 与三层变更工作流

版本 techv_0.2；2026-09-20。依据用户硬性要求：任何项目变更必须经过“技术设计 → 测试 → 实现”。适用于人和 AI agent、功能、修复、重构、依赖、构建/CI、配置、迁移、UI、原型、文档；“只是小改”不能跳过流程。

<a id="td-tdd-order"></a>
## 1. 不可跳过的顺序

```mermaid
flowchart LR
  D["技术设计 · 契约/影响/验收"] --> T["先写测试"]
  T --> R["RED · 验证预期失败"]
  R --> I["最小实现"]
  I --> G["GREEN · 目标与回归通过"]
  G --> F["重构 · 持续 GREEN"]
  F --> E["证据/审查/合入"]
```

1. 先建立 CHG 记录：需求来源、变更原因、输入输出/边界/不变量、影响、兼容、风险、回滚及验收。引用已存在设计可以，但必须解释本次增量；行为改变先同步技术设计，重大取舍写 ADR。
2. 从契约编写自动化测试，确认针对尚未实现行为得到预期 RED。失败必须可解释，缺依赖/测试编译错/网络不可用不算业务 RED。
3. 只实现让当前测试通过的最小行为；不得先写成品再回填 RED。一次功能较大时拆垂直切片，每片都独立循环。
4. GREEN 后运行相应回归、架构/类型/格式与门禁，再重构；重构期始终保持行为测试 GREEN。
5. 记录实际命令、退出码、失败断言、执行环境和证据，审查设计与测试是否覆盖改变的行为，再合入。

技术设计也有测试：文档链接、需求完整性、规则冲突/例子/接口一致性；这些不能代替实现阶段真正运行产品的测试。用户要求输出文档时可停在文档变更完成，不擅自开发全部产品。

<a id="td-tdd-evidence"></a>
## 2. 每次变更的最小证据

使用[变更模板](../changes/TEMPLATE.md)。记录不依赖记忆或口头“测过了”，至少包含：

| 字段 | 要求 |
| --- | --- |
| changeId | CHG-YYYYMMDD-NNN；与 PR/提交关联 |
| requirements/designRefs | func/工程规则 ID、精确设计章节、ADR |
| acceptance | 正向、失败、边界、外部副作用的可验证描述 |
| baseline | RED 所依赖的基线 commit/tree；记录工具链和 lockfile |
| designRevision | 含本次设计、无对应实现的阶段引用 |
| testRevision | 含设计和新增测试、仍无该行为实现的阶段引用 |
| red | 命令、预期失败 case ID、实际断言、退出码、日志 artifact/hash |
| implementationRevision | 正式实现阶段引用，禁止引用将来的占位 SHA |
| green | 同一测试命令的实际通过结果 + 必要回归 |
| review | 对契约、范围、测试价值和风险的核验结论 |
| delivery | 已实现/仅设计/有阻塞分别注明，不使用虚构通过状态 |

功能/修复要求同一新增断言在测试阶段失败、实现阶段通过。修复必须能在旧实现重现问题。与需求无关的失败不能用作 RED。

证据日志不得包含真实 Secret 或业务数据。工具自动产生时间、命令、退出码及日志 hash；自写 Markdown 可以解释，但不能替代机器日志和 CI 复验。测试输出哈希不承担绝对证明开发思维顺序的功能；可信执行、提交阶段和审查共同约束流程。

## 3. 不同变更类型的测试方式

| 变更类型 | 技术设计 | 先行测试与 RED |
| --- | --- | --- |
| 新功能/修复 | 新/修改契约与状态、副作用 | 新行为失败/旧 bug 重现，再实现修复 |
| 纯重构 | 声明保持的不变量与允许改动边界 | 先补 characterization；旧实现可 GREEN，再用代表性 mutation 验证断言能 RED；重构后维持 GREEN |
| 性能 | 输入规模、基线、预算和测量环境 | 可重复 benchmark 超预算 RED，不能靠降低预算伪造通过 |
| 依赖/构建/配置 | 兼容矩阵、运行行为和回滚 | 升级目标的契约/打包测试，或先用不兼容 fixture/mutation 验证检测能力，再修改依赖 |
| 数据迁移 | 旧/新 schema、默认值、事务及回退 | 从旧库触发新需求失败，迁移后成功；另测失败原子性 |
| UI/视觉 | 用户操作/可访问性/目标视觉与布局 | 先行为断言，再目标状态截图差异；审查新基线，不能批量接受全部差异 |
| 纯测试 | 测试要保障的契约与现有缺口 | 代表性错误实现/mutation 必须被新测试杀死；修正测试后证明正常输入通过 |
| 文档/治理 | 文档契约、链接/追踪/例子语义 | 缺少目标文档、断链、缺需求或错误例子的检查先失败，再补内容 |
| 删除能力 | 消费者、数据保留和兼容决定 | 验证被禁止入口/依赖不可再调用、历史仍可读，再删除实现 |

纯重构不要求把正确旧行为故意改坏并提交；mutation 在临时隔离目录执行且清理，不进入产品代码。既有测试足以覆盖的小修也需指定它、运行其敏感性检查并记录设计依据。无可运行行为的文案修正，先定义文档断言/检查；不能编造业务测试。

## 4. 文档和本次自举

本次 CHG-20260920-001 先写变更设计，再新增 Node 内置文档测试，得到缺设计产物的 RED，再创建技术设计文档、矩阵与规范。当前只有文档测试实际实现；所有产品 TC 场景仍是规格。

文档测试核验产物、相对链接/显式锚点、PRD func 完整覆盖、测试场景引用和项目入口。它不判断每个技术方案正确，也不证明“覆盖了全部边界”；人工/agent 按验收契约复核仍必须进行。

原型文件是设计资产，但其交互脚本改变了用户可观察行为时，必须新增/更新相应交互测试；不能把可运行原型归为文案来逃避测试。自动生成文件可复用源变更的设计/测试证据，但必须验证可重生成与无额外手工改动。

工程工具首次建立时先用 Node 自带运行器测试 gate 的输入/输出反例，再实现 gate；首次无法引用尚不存在的旧 gate 时，由独立已存在的文档/契约校验与真实 RED 日志完成自举。不得据此把以后所有 gate 修改当作“自举例外”。

<a id="td-tdd-gates"></a>
## 5. 自动化门禁设计

M0 必须实现以下 gate，业务切片开始前建立。当前仅为设计，实际状态见末节。

### G1 变更追踪

相对 merge-base 枚举所有修改/新增/删除路径，每条必须被 CHG 覆盖；校验 designRefs、需求/工程 ID、测试路径、变更类型及 evidence。缺设计、缺验收、tests=[]、不可解析引用、伪造/空白日志都拒绝。工具读取白名单内结构化数据，不执行 CHG 中任意 shell 文本。

文档/工具新增的追踪需求与 func 无关时使用 ENG-*；不能强行虚构产品 func。锁文件、生成文件、CI、AGENTS 也在范围内，通过来源关系免重复写描述但不免检查。

### G2 重放 RED/GREEN

以受信任的固定命令模板和声明的 test ID 运行，禁止提交者任意构造“返回 1 即成功的测试”。建立隔离 checkout：

1. designRevision 是基线后祖先，仅设计允许变更。
2. testRevision 在 designRevision 后，包含测试/fixture及必要类型骨架，不含该功能实现。
3. 该版本目标测试必须出现指定契约断言失败；记录 case ID 和原因，不接受仅 import error/安装失败。
4. implementationRevision 在 testRevision 后，相同测试和最终必要回归通过。
5. 重构/测试/配置的替代 RED 按上表在隔离 mutation/fixture 上复验，正常分支始终通过。
6. 验证最终 diff 的生产变更与 CHG 范围一致；禁止删断言、改 expected、skip/only、降低门槛来通过。

测试必需的类型/接口骨架须以设计定义的“抛 NotImplemented”或空端口存在，让 RED 落在目标断言上；不得提前写出实现。极小纯文档变更可通过提交前工作树补丁与 CI 保存的阶段 artifact 复验，但同样必须保留设计/测试/实现次序与相同断言，不能只提供一份最终 GREEN。

平台相关目标在对应受信 runner 重放：例如 macOS Keychain、Electron 原生进程与打包测试，其 RED/GREEN 使用同一 OS/架构/锁定工具链。Linux tdd-gate 只协调、校验和汇总；平台证据缺失或 skip 不得通过。平台清单不能由 PR 自选缩减，证据须绑定阶段 tree、测试 ID、命令模板、工具链和本次 CI job，详见[CI 矩阵](testing_strategy.md#td-tests-ci)。

默认保留 D/T/I 三阶段提交；主分支只合入完整 GREEN 的变更分支。禁止丢失阶段证据的 squash；若需要压缩历史，先由受信 CI 归档不可变阶段 bundle 和复验结果，并能根据 bundle 重放。提交时间戳和用户自报日志都不是可信证据本身。

### G3 测试与质量

类型、lint、架构规则、文档追踪、适用的 unit/integration/contract/component/e2e/visual 全部通过；覆盖率只对已实现代码衡量，不能用空项目 100% 冒充。门槛见[测试策略](testing_strategy.md#td-tests-gates)。禁止未说明 skip、test.only、吞错误、真实网络偶然成功作为确定性单元测试。

### G4 可信执行与保护

最终 required check 名称固定为 tdd-gate、quality、integration、desktop-e2e（涉及应用时）、docs。gate 实现和 workflow 取受保护基线/固定可复用工作流，不能从被审查 PR 中加载其修改版后让它验证自己；gate 改动先经过旧 gate 测试及独立审查。

对来自 PR 的代码运行无生产凭证沙盒环境，默认只读 GitHub token；不用 pull_request_target 搭配 checkout 不可信代码执行。阶段证据存 CI artifact，并在合入记录中保存 artifact ID/摘要；保留期至少覆盖发布审计周期，不能只留下将过期链接。

GitHub main 规则集要求 PR、required checks、禁止 force push/删除、无管理员绕过；gate/workflow 修改需独立审查者。配置规则集属于外部仓库设置，本次未修改。单维护者无法独立审查或账号方案不支持规则集时，必须如实记录剩余人为绕过风险，不得宣称“绝对技术保证”。

任何人均能在自己的本地绕过 Git hook；因此 pre-commit/pre-push 只作反馈，强制约束依赖远端 required checks。项目规范不允许紧急修复跳过 TDD；可缩小变更，但仍需先有设计与复现。

## 6. 测试驱动示例：Header 变量

设计先声明：Header 只接受字符串；每个变量必映射；对象创建后变量不可改；null/缺字段为 not_evaluable，数值 123 为 failed / INPUT_TYPE_MISMATCH；不发 HTTP。

测试先给映射值 123、0、false、null、空白和字符串分别断言，检查 transport 调用次数为 0 或 1。记录旧代码错误地字符串化 123 的 RED，再实现严格类型检查。GREEN 后验证合法字符串原样发送、auth/Header 冲突、不可编辑、快照隔离与计划映射保存。不能只测试内部函数“被调用”。

## 7. Definition of Ready / Done

Ready：CHG 完整、设计边界明确、产品语义无未决冲突、可执行验收场景已选、测试环境可用。外部密钥未提供时可做纯领域/Mock 切片，但真实集成完成状态不可提前勾选。

Done：设计与代码一致；RED 有效；GREEN 与所需回归实际通过；数据兼容/迁移/安全/性能影响已验证；文档与矩阵更新；无副作用扩大；远端 gate 通过后方可合入。设计交付的 Done 则是文档自身通过验收，并准确标识产品测试尚未实现。
